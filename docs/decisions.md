# Decisions

Notes on nontrivial choices, and on findings confirmed directly against reference-project source rather than assumed. See CLAUDE.md for the licensing/attribution policy governing what reference projects may be used for.

## Lich frontend-port handshake (confirmed against lich-5 source, 2026-09-13)

TASKS.md's "Connection to Lich" section warned not to assume ProfanityFE's `SET_FRONTEND_PID` convention verbatim without checking lich-5's own listener code. Confirmed directly:

- **The listener is opt-in, not always-on.** Lich only opens a frontend/detachable-client TCP socket when started with `--detachable-client=VALUE` (accepted forms: `PORT`, `auto`, `HOST:PORT`, `[IPV6]:PORT`; `auto` lets the OS assign a port). Default bind host is `127.0.0.1` unless `--bind-address` overrides it. See `lib/main/detachable_client_target.rb` and `lib/main/main.rb` (around the `detachable_client_thread` block).
- **`SET_FRONTEND_PID <pid>` is real and lich-5 does parse it** (`lib/global_defs.rb`, `handle_detachable_client`, matching `/^SET_FRONTEND_PID\s+(\d+)\s*$/`), matching ProfanityFE's convention. It is optional, not a required identify/auth step -- the socket accepts and dispatches input with or without it. It only feeds `Frontend.set_from_client`, used for frontend-differentiated behavior elsewhere in Lich.
- **On accept, Lich immediately pushes initial state** to the new client: vitals progress bars (mana/health/spirit/stamina), status indicators, prepared spell, and compass exits (`detachable_client_send_init`). It does **not** include room description, room objects, or room players -- so grimoire still needs to auto-send `look` on first prompt to populate those, per TASKS.md.
- **Outgoing protocol is plain newline-terminated text lines.** Lich's own detachable-client handler prepends its internal `$cmd_prefix` (`'<c>'`) server-side before dispatching each line (`lib/global_defs.rb`, `handle_detachable_client` / `dispatch_client_input`). Grimoire must never send `<c>` itself -- that tag is added by Lich, not expected from the client.
- **The actual Lich script-command prefix character is `;`** (or `,` for the Genie frontend) -- `$lich_char` / `$lich_char_regex` in `lib/main/main.rb`. This is what a local `.command` -> `;command` passthrough rewrite in grimoire's input box would target; it is a grimoire-side UX convenience, not something the protocol requires (typing `;command` directly works with no rewriting at all).
- **Connect-failure and mid-session-drop are genuinely different code paths on the Lich side too**: the accept loop's `rescue` (server-side accept errors) is distinct from `client.gets` returning `nil` on the per-client read loop (clean EOF/disconnect). This confirms TASKS.md's note (and the bug rift-nexus hit) that grimoire's own TCP client needs separate handling for "never connected" vs. "connected, then dropped."

Sources: `_references/lich-5/lib/main/detachable_client_target.rb`, `_references/lich-5/lib/main/main.rb`, `_references/lich-5/lib/global_defs.rb` (`detachable_client_send_init`, `handle_detachable_client`, `dispatch_client_input`, `do_client`).

## pushStream/popStream is a single current-stream value, not a nested stack (confirmed against lich-5 source, 2026-09-13)

TASKS.md's Stream parsing section called this "Id-aware pushStream/popStream stack tracking." Confirmed directly against `_references/lich-5/lib/common/xmlparser.rb`: Lich's own reference parser tracks a single `@current_stream` value plus an `@in_stream` flag -- `pushStream` overwrites `@current_stream` with the new id (there is no push onto a saved stack), and `popStream` always drops back to narrative regardless of any id it carries or of what was open before. A `pushStream` seen while already inside another stream simply replaces the current id; the original is not restored when the inner one closes. The real protocol never nests streams, so there is nothing to restore.

`Grimoire::StreamTracker` (`lib/grimoire/stream_tracker.rb`) implements this single-current-value model rather than a literal stack, to match confirmed behavior instead of the stronger semantics the task wording implied.

Source: `_references/lich-5/lib/common/xmlparser.rb` (around the `pushStream`/`popStream` handling in the tag-open callback).

## Executable launcher lives at the repo root, not in a gem `exe/` directory (2026-09-13)

The initial pass at the launcher put it in `exe/grimoire` with `spec.bindir`/`spec.executables` set in `grimoire.gemspec`, following plain RubyGems convention (mirrors how `bundle gem` scaffolds a new gem). That convention exists to support `gem install` copying the file onto `PATH` and RubyGems auto-activating `lib/` for it.

Grimoire will never be `gem install`ed -- "Packaging/distribution" is explicitly out of scope for MVP (see TASKS.md), and the only distribution paths are a git clone or a source archive, same as `lich-5` itself. Building the launcher's location around an install mechanism that will not be used is designing for a requirement the project has explicitly deferred. The launcher was moved to a root-level `grimoire` script (matching `lich.rbw`'s own placement, for the same reason: no packaging layer to hand it off to), using `require_relative 'lib/grimoire'` instead of a bare `require 'grimoire'` since it can no longer rely on RubyGems/Bundler activating `lib/` for it as an installed executable. `spec.bindir`/`spec.executables` were removed from the gemspec accordingly.

The gemspec itself was kept (not folded into a plain `Gemfile` with inline `gem` lines): `Gemfile`'s `gemspec` directive still needs it for the `gtk3`/`rspec`/`rubocop` dependency declarations and for `spec.require_paths = ['lib']`, which is what puts `lib/` on the load path for `bundle exec`. That mechanism is orthogonal to whether the gem is ever published -- it is what makes local development work at all, so removing it would only add cost (re-wiring the load path some other way) with no offsetting benefit.

## Room transitions and periodic room updates are two distinct events (confirmed against captured GS session logs, 2026-09-13)

TASKS.md's "Structured room state" item cannot be a single "on room tag, replace room state" handler -- real traffic shows two genuinely different triggers that a room-state tracker must handle differently:

- **Move-triggered transition (new room):** entering a new room via a move action (`north`, `south`, etc.) arrives bracketed by `<clearStream id='room'/><pushStream id='room'/>`, carries `<compDef id='room desc'|'room objs'|'room players'|'room exits'>` for all four fields together, and is keyed by a room identity change via `<nav rm='NNNN'/>`. This is a full reset: the previously known room state is discarded and replaced wholesale.
- **Periodic/passive update (same room):** already visible in `lich-5/benchmark/fixtures/gs_sample.xml` -- bare `<component id='room objs'>` / `<component id='room players'>` tags recur repeatedly mid-combat with **no** accompanying `<nav>` and **no** `clearStream`/`pushStream id='room'`/`compDef` bracket (e.g. another creature's death changing what "you also see," or a player entering/leaving). This is a partial merge into the currently-known room, not a new room -- the identity (title, description, exits, room number) has not changed and must not be reset or cleared just because an objs/players field arrived.

**Implication for the tracker's design:** it needs two entry points, not one -- `enter_room(...)` (fires only on the `nav rm=`/`clearStream`+`pushStream id='room'` bracket; resets every field) and `update_room(...)` (fires on a bare `component id='room objs'|'room players'` outside that bracket; merges into whichever fields it names, leaves the rest untouched). Treating every `room objs`/`room players` tag as transition evidence would spuriously "enter" a new room on every passive update.

**Implication for fixtures:** the planned `spec/fixtures/` split (see conversation, not yet built) needs a `room_transition.xml` (move-triggered, full bracket, from the session-logs GSF capture) *and* a separate `room_update.xml` (passive, bare component tags, already extractable from the existing `gs_sample.xml` reference) as two distinct examples -- one file covering both would blur the exact distinction this note exists to preserve.

## Orphaned line terminator after a fully-squelched line (found and fixed, 2026-09-13)

Sibling project rift-nexus's `client/display_filter.py` documents (`docs/decisions.md` there) hitting a real bug: `<prompt>` is resent far more often than once per player action, and squelching only its content left a run of near-empty lines in the display -- fixed there with a post-hoc regex that collapses runs of 3+ newlines down to 2, since that filter has no real tag boundaries to reason about.

Grimoire's `NarrativeStream` has real tag boundaries (via `Tokenizer`/`StreamTracker`/`PromptTracker`/`RoomTracker`), so it was worth checking directly rather than assuming the tokenizer-based design was immune. It was not: fed realistic per-line CRLF input (matching how `Connection#read_loop` actually delivers lines, one `socket.gets` call at a time), any tag squelched in full that happened to occupy an entire wire line -- a lone `<prompt>`, a bare `<component id='room objs'|'room players'>`, or a whole `pushStream`/`popStream` bracket -- left that line's own terminator behind as an ordinary `Text` token, since it arrives *after* the relevant tracker has already flipped back to narrative and so is indistinguishable, in isolation, from real content. Confirmed via a throwaway script feeding exactly this shape of input before any fix existed.

**Fix (original, since revised below):** rather than porting rift-nexus's after-the-fact blank-run collapsing (which would re-introduce a dumb-regex layer this project deliberately avoided -- see CLAUDE.md's "Stream parsing" ground rule), `NarrativeStream` tracks the transition itself: when the combined narrative decision flips from squelched to narrative, it remembers that the *next* text token may carry a stranded terminator, and strips exactly one leading `\r?\n` from it. Only one terminator is stripped per transition, so a genuinely blank line immediately after (real narrative spacing, or -- as it happens -- the blank separator lines `room_transition.xml`/`room_update.xml` insert between spliced-together excerpts from different points in the same session) is left alone. See the "orphaned line terminators after a squelch" spec group in `narrative_stream_spec.rb`.

**2026-09-13, later the same day -- revised again, see "Squelched-line separator kept instead of dropped" below:** the mechanism described just above (a single `@pending_line_strip` flag, since renamed/restructured) *deleted* every stranded terminator outright, which turned out to be too aggressive once checked against a real live capture rather than just fixtures -- see that entry for what changed and why.

## Squelched-line separator kept instead of dropped, capped at exactly one per gap (found live, fixed 2026-09-13)

`--autolog` against a real live session (`log/session-8000-20260913-161027-{raw,parsed}.log`, not committed -- see `.gitignore`) showed the original fix above was an over-correction: it deleted *every* stranded terminator after a squelched line, not just the redundant ones, so two genuinely distinct completed outputs separated only by a squelched `<prompt>`/`<component>`/dialogData line ran together with no blank line between them at all (e.g. "Cast Roundtime 3 Seconds." directly followed by "Nodens slides a tapered..." on the very next line, no gap) -- confirmed by replaying the raw log through `NarrativeStream` and diffing against the parsed log byte-for-byte (an exact match, ruling out stale output before treating it as a real bug). `narrative_stream_spec.rb`'s own "orphaned line terminators after a squelch" group had in fact pinned this zero-separator behavior down as the expected result, so the fix that follows is a deliberate reversal of that group's original assertions, not just a new case.

**Fix:** `NarrativeStream#resolve_boundary` (plus `artifact_separator`/`genuine_blank`) replaces the single delete-on-sight flag with three pieces of state: `@seen_real_content` (sticky; before any real narrative text has ever appeared, a squelched line's own terminator is still pure noise and dropped, so a squelch-only fixture or a squelch right at session start does not leak a leading blank line), `@gap_separator_emitted` (reset whenever real content is emitted; caps the surviving separator to exactly one per gap, whether that gap holds one squelched line, several in a row, or a squelched line immediately followed by a genuinely blank line the game itself sends -- none of those combinations should stack up more than the single blank line a reader expects between two completed outputs), and `@at_line_start` (distinguishes a bare terminator that is only finishing the current output line -- e.g. the trailing `\r\n` after `Obvious paths: <a...>out</a>`, split into its own token by the `</a>` boundary -- from one that represents an actual blank row; only the latter is subject to the separator cap at all, otherwise ordinary mid-line terminators would be misread as extra blank rows). Verified against the same live capture (replayed and re-diffed: every completed output now has exactly one blank line before the next, with no doubles even where a squelched line and a genuine blank line land back to back) and against the full spec suite, including updated fixtures for the multi-squelched-line and start-of-session cases in `narrative_stream_spec.rb`'s "orphaned line terminators after a squelch" group.

## Lich never echoes a submitted command back; the frontend must do it locally (found live, fixed 2026-09-13)

A ">>> <command>" line in a sample under `_references/session-logs/` was initially taken as Lich echoing a submitted command back over the wire, and `NarrativeStream` was given a rewrite (`COMMAND_ECHO_PATTERN`) to turn it into `"<prompt_char> <command>"`. Two real `--autolog` captures against an actual Lich frontend-port connection (`log/session-8000-20260913-{161027,165033}-{raw,parsed}.log`, not committed -- see `.gitignore`) showed this assumption was wrong: neither log contains `>>>`, or any other command echo, anywhere -- confirmed by grepping both raw logs directly. Lich's detachable-client protocol simply never echoes a submitted command back at all; the `_references/session-logs` sample most likely came from a different kind of client/capture (e.g. a terminal session where the terminal's own local echo of what was typed got captured alongside the game's output), not a raw frontend-port socket dump.

Checked against `ProfanityFE`'s own architecture for how a real Lich frontend handles this (behavior only, per CLAUDE.md's GPLv2 licensing note -- no code or structure copied): its `send_command` calls `@window_mgr.add_prompt(window, @shared_state.prompt_text, cmd)` to write the submitted command into its own main scrollback window immediately on send, independent of anything coming back from the server. That confirms the split: the frontend, not Lich, is responsible for showing a typed command.

**Fix:** `App#handle_command` (`lib/grimoire/app.rb`) now displays `"\n#{prompt_char} #{command}\n"` before enqueueing the command, so a submitted command is always shown regardless of whether the wire ever echoes anything. `prompt_char` is threaded through from `App.new`'s own keyword (default `NarrativeStream::DEFAULT_PROMPT_CHAR`, `'>'`) into both `NarrativeStream` (for the now-confirmed-unnecessary-but-harmless wire rewrite) and the local echo, so both stay in sync under one setting; making that setting user-configurable beyond the default is still a later task, per the original request. `NarrativeStream`'s `COMMAND_ECHO_PATTERN` rewrite is left in place as a no-op safeguard in case some Lich/game configuration ever does echo this way, but is not what real usage depends on -- see the corrected comments at its definition and in `narrative_stream_spec.rb`'s "command echo rewriting" group. Covered by `spec/grimoire/app_spec.rb` (new file): default and custom `prompt_char` echo, the command still reaching the command queue, and the auto-issued `look` on the first prompt going through the same path (so it is echoed too, deliberately, as a locked-in regression case rather than an unexamined side effect).

## GUI-panel/status tags squelched wholesale, temporarily (found live, fixed 2026-09-13)

`--autolog` was used against a real live Lich session (`log/session-8000-20260913-153637-{raw,parsed}.log`, not committed -- see `.gitignore`) specifically to check the orphaned-terminator fix above against real traffic rather than just fixtures/synthetic input. It held up perfectly (confirmed by replaying the raw log through the fixed `NarrativeStream` and diffing), but the live capture surfaced a second, unrelated problem the fixtures never exercised: the parsed log had 54 blank lines against only 16 genuinely blank raw lines, and one line of real garbled text (`Nonegreen crackersEmpty`).

Both traced to the same cause: none of `StreamTracker`/`PromptTracker`/`RoomTracker` know about a wider family of GUI-panel/vitals-status tags than TASKS.md's "Route non-narrative panel tags" item had enumerated. Confirmed present in the live capture: `dialogData`, `openDialog` (from the earlier `panel_dialogs.xml` fixture, not re-seen live but same shape), `roommeta`, `spell`, `left`, `right`, `indicator`, `progressBar`, `resource`, `style`, `skin`, `image`, `pulse`, `label`, `compass`, `castTime`. Two distinct symptoms, one root cause:

- **A raw line made entirely of these tags** (e.g. a lone `<roommeta weather="0" .../>`, or a multi-tag `<dialogData>...</dialogData>` block) has no real `Text` token of its own for the line's trailing CRLF to belong to, so it survives as a bare blank line -- all 38 of the extra blank lines were exactly this shape, confirmed by replaying the raw log and flagging every non-blank raw line that produced whitespace-only output.
- **Adjacent instances on the same line with no real narrative between them** leak with no separator, because none exists on the wire between them either: Lich's initial vitals push has `<spell>None</spell>` immediately followed by indicator tags then `<right>green crackers</right><left>Empty</left>`, which is exactly the `Nonegreen crackersEmpty` line -- not a case of a real newline being removed, just structured status data with no narrative shape being displayed as if it were prose.

**Fix:** `lib/grimoire/panel_tag_tracker.rb` (`PanelTagTracker`), wired into `NarrativeStream` alongside the other trackers. Squelches this tag list wholesale -- content dropped, not routed anywhere -- the same "drop tag and content" approach sibling project rift-nexus converged on for the same category of tag in its own `display_filter.py` (no code or structure taken from it, same agreement on approach only). Because `PanelTagTracker` reports these regions as non-narrative through the same `narrative?` interface as every other tracker, the orphaned-terminator fix above applies to it automatically with no extra wiring -- a lone squelched status line now correctly produces nothing at all, not even a blank line.

**Explicitly temporary** -- this is deliberately not the long-term home for this data. TASKS.md's "Route non-narrative panel tags to structured state" item stays open and unchecked; `PanelTagTracker`'s own comment carries the same marker. Revisit if any of these tags turn out to carry information a future UI needs (`spell`/`left`/`right` for a prepared-spell/hands indicator) -- at that point the tag moves out of `DROP_TAGS` and into real structured state instead, the same migration path `component id='room objs'|'room players'` already took into `RoomState`, and `progressBar`/`indicator` have now taken too (see below).

## Vitals/status tags routed into structured state, confirmed against real traffic rather than `uberbar_eo.lic` (2026-09-13)

TASKS.md's "Route non-narrative panel tags" item flagged `progressBar`/`indicator` as the next candidates to migrate out of `PanelTagTracker`'s wholesale squelch once a UI wanted vitals data (the deferred "Basic vitals/indicator area" item). Before writing `VitalsTracker`, `_references/uberbar_eo.lic` (a community Lich script for Wrayth, surfaced as a possible starting point) was evaluated and rejected as a code/architecture source:

- It runs *inside* Lich, reading already-parsed state off `Char`/`XMLData`/`Stats`/`Resources` and pushing a *new* custom dialog overlay (`openDialog`/`dialogData`/`skin`/`label`/`image`, anchor-chained positioning, Wrayth-bundled image names like `healthBar`/`InjuriesPanel`) back out over the same socket -- the reverse of what grimoire needs, which is to parse vitals directly off the incoming wire stream.
- Its `skin`/`image`/anchor layout only means anything to Wrayth's own dialog renderer and asset bundle; grimoire (GTK3) has no equivalent and has no reason to replicate a proprietary third-party dialog shape.
- It tracks silver/bounty/ATP/TP/percent-capped/wound-and-scar body locations, well beyond TASKS.md's stated MVP vitals scope, and has **no roundtime handling at all** despite that being one of the two things named in the "vitals/indicator area" task.
- It comes from `elanthia-online/scripts`, a source not covered by CLAUDE.md's licensing/attribution section (only `lich-5`, `ProfanityFE`, `rift-nexus`, and Wrayth/Stormfront are audited there) and carries no license header of its own -- unaudited, so nothing was transliterated from it regardless of the architectural mismatch.

Instead, the native tag shapes were confirmed directly against two real `--autolog` captures (`log/session-8000-20260913-153637-raw.log`, `log/session-8000-20260913-155347-raw.log` -- not committed, see `.gitignore`; the same captures used for the GUI-panel-tag entry above), by grepping the raw logs rather than the already-`PanelTagTracker`-filtered parsed logs. Confirmed present and self-closing (no matching close tag, unlike `RoomTracker`'s `compDef`/`component` brackets):

- `<progressBar id='health'|'mana'|'stamina'|'spirit' value='PCT' text='name cur/max'/>` -- the four core vitals, each later reappearing with `left='0%'|'25%'|'50%'|'75%' customText='t' top='0%' width='25%' height='100%'` (a four-quadrant minivitals-strip layout).
- `<progressBar id='mindState' value='PCT' text='must rest'/>` (sometimes carrying bundled `field_exp`/`max_field_exp`/`ascension_exp`/`exp`/`until_next` attributes on the same tag), `<progressBar id='pbarStance' value='N'/>` (no `text` attribute at all), `<progressBar id='encumlevel' value='PCT' text='None'/>`.
- `<indicator id='IconBLEEDING'|'IconDISEASED'|'IconKNEELING'|'IconPOISONED'|'IconPRONE'|'IconSITTING'|'IconSTANDING' visible='y'|'n'/>` -- one self-closing tag per status icon, toggling `visible` in place rather than being added/removed.
- Noise confirmed present in the same `progressBar` tag family that must **not** be treated as a vital: numeric-id buff/spell-timer bars from the Active Spells window (e.g. `id='1125' text="Troll's Blood"`, carrying a `time='HH:MM:SS'`/`'Indefinite'` attribute vitals bars never have) and the experience bar (`id='nextLvlPB'`).

**Design:** `lib/grimoire/vitals_state.rb` (`VitalsState`, a plain holder -- `health`/`mana`/`stamina`/`spirit`/`mind`/`encumbrance` as a `percent`+`text` pair, `stance` as a bare percent, `indicators` as a flat id => visible hash with no fixed icon list assumed) plus `lib/grimoire/vitals_tracker.rb` (`VitalsTracker`). Because every relevant tag is self-closing on the wire, the tracker needs no open-container bracket state the way `RoomTracker`/`PanelTagTracker` do for their multi-tag regions -- each `progressBar`/`indicator` token is routed independently. Recognized ids populate `VitalsState`; unrecognized ones in the same two tag families (buff timers, `nextLvlPB`, any indicator id not yet seen) are still reported as non-narrative so they do not leak into the scrollback, but are not exposed anywhere -- the same "capture but do not expose" middle ground `PanelTagTracker` still uses for its own remaining tag list. `progressBar` and `indicator` were removed from `PanelTagTracker::DROP_TAGS` accordingly; everything else there is unaffected. Real fixture: `spec/fixtures/vitals.xml`, extracted from the same two raw logs with source-line citations, exercised at the `NarrativeStream` level (not tokenizer-only, since narrative-level filtering no longer depends on an open item for these two tags).

## VitalsTracker derives health/mana/stamina/spirit percent from text, not value (found live, fixed 2026-09-13)

Reported live: the vitals strip (see the "Basic vitals/indicator area" TASKS.md entry) did not show correct percentages immediately on attaching grimoire to an already-live Lich session -- it looked like it was waiting for some periodic refresh. Traced into `lich-5` (`_references` does not carry `lib/global_defs.rb`; checked against the sibling `lich-5` workspace repo directly, read-only): `detachable_client_send_init` (the one-time push a newly-attached frontend gets, see the "frontend-port handshake" entry above) hardcodes `value='0'` for exactly `health`/`mana`/`stamina`/`spirit`, regardless of the character's actual vitals, even though the `text` attribute on the same tag carries the correct `"<label> current/max"` numbers. This is not hypothetical -- it is reproduced verbatim in our own `spec/fixtures/vitals.xml`'s init line (`<progressBar id='mana' value='0' text='mana 132/655'/>` etc., health full at 355/355 reported as `value='0'`). `mindState`/`encumlevel`/`pbarStance` are unaffected -- Lich's init computes those correctly.

Checked `ProfanityFE` (behavior only, per CLAUDE.md's GPLv2 licensing note) to see whether a mature frontend already has to work around this: it does. `lib/tag_handlers.rb#handle_progress_bar_tag` never uses `value` at all for GemStone-style health/mana/stamina/spirit -- it matches `text`'s `current/max` numbers and computes the bar from those exclusively.

**Fix:** `VitalsTracker::FRACTION_TEXT_IDS` (`health`/`mana`/`stamina`/`spirit` -- the four ids whose `text` is shaped like a fraction; `mindState`'s "must rest" and `encumlevel`'s "None" are not, so they keep using `value` unchanged) plus `#percent_for`, which parses `text` for `current/max` and computes `(current * 100) / max` (integer floor), falling back to the wire's `value` if `text` is missing, unparseable, or has a zero max. Floor division was chosen deliberately over rounding: it exactly reproduces Lich's own `value` on a real (non-init) update -- `spec/fixtures/vitals.xml`'s `value='98' text='health 351/355'` is precisely `(351 * 100) / 355 = 98` -- so the fix is a no-op for ordinary traffic and only changes the result for the documented init-push bug (or any other value/text inconsistency for these four ids). `spec/grimoire/vitals_tracker_spec.rb` covers the bug reproduction (`value='0' text='mana 132/655'` -> 20%), the fallback paths (no fraction in text, zero max), and confirms `mindState`/`encumlevel` are untouched even if their text coincidentally contained a fraction. `narrative_stream_spec.rb`'s vitals fixture test updated accordingly: `spirit` (10/10 on the wire, `value='0'` in the fixture's init line) now correctly reads 100%, not the previously-pinned buggy 0%.

Separately, live capture during this investigation also turned up a genuine `lich-5` bug unrelated to grimoire's own code: `detachable_client_send_init`'s first line waits up to 10 real seconds on `XMLData.indicator['IconJOINED']` (a bare truthiness check against a group-membership flag, not `== 'y'` the way `checkgrouped` in the same file does it) before sending *any* init data, and that wait accomplishes nothing functionally since nothing downstream branches on it. Recommended fix (a one-line removal) prepared on a local `IconJoined_delay` branch in the `lich-5` checkout for potential upstream contribution -- out of scope for grimoire's own repo/fix.
