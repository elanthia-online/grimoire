- [x] Main window: scrollback text view plus command entry (MVP shape, matches rift-client's minimal starting point) — `lib/grimoire/window.rb`

- [x] Echo a submitted command to the scrollback — Lich's detachable-client protocol never echoes it back over the wire, confirmed against two real captured sessions (see `docs/decisions.md`), so the frontend must show it itself, the same split `ProfanityFE` uses — `App#handle_command` (`lib/grimoire/app.rb`), format `<prompt_char> <command>` with `prompt_char` a constructor keyword defaulting to `NarrativeStream::DEFAULT_PROMPT_CHAR` (`>`); making it user-configurable beyond the default is still open
- [x] Basic vitals/indicator area (health, mana, stamina, roundtime) fed by structured stream state — stretch goal, may land after the first working scrollback-and-input loop. Health/mana/stamina/spirit/mind/encumbrance/stance bars plus an active-indicators label now land in `Window#build_vitals_strip`/`#update_vitals`, fed from `App#handle_line` on every line (not gated behind `text.empty?`, since a vitals-only line carries no narrative text at all) — see `window_spec.rb`'s `#update_vitals` group and `app_spec.rb`'s "refreshes the vitals strip" case. Roundtime now lands too, tracked as two independent locks but rendered as one progress bar: `VitalsTracker` routes the self-closing `<roundTime value='EPOCH'/>` (hard roundtime, from most actions, confirmed against `lich-5`'s own `xmlparser.rb` source since no captured session log happens to contain one) and `<castTime value='EPOCH'/>` (cast roundtime, from spell preparation, already seen live in `spec/fixtures/vitals.xml`'s sibling raw-log excerpts — moved out of `PanelTagTracker::DROP_TAGS` accordingly) tags into `VitalsState#roundtime_end`/`#cast_roundtime_end`. Per the user's own placement/behavior spec (see `docs/decisions.md`, superseding two earlier label-based attempts that were both reported as having no visible indicator): a single `Gtk::ProgressBar` sits left of the command entry (`#build_window`'s `command_row`, not the vitals strip), sized to ~60% of the health bar's natural width and matched to the entry's own height (`Window::ROUNDTIME_BAR_WIDTH`/`BAR_HEIGHT`, both GTK-measured rather than guessed), reading `RT: <n>` directly embedded on the bar (`n` = whichever of hard/cast has more time left) and full at 10 seconds or more (`Window::ROUNDTIME_FULL_SECONDS`). The text is a separate left-justified/bold/white `Gtk::Label` (`Window::ROUNDTIME_TEXT_CSS_CLASS`) composited on top of the bar via `Gtk::Overlay`, not the bar's own `show_text` — that overlay does not actually draw over the trough in this GTK/theme combination (confirmed by measuring: `trough` and `text` are separate CSS nodes that stack vertically here rather than one drawing over the other), and has no public alignment/weight/color control regardless — see `docs/decisions.md`. Color tracks hard roundtime specifically — health-red while it is still running, mana-blue once it has ended but cast roundtime continues — toggled live via `style_context.add_class`/`remove_class` in `#update_roundtime_bar`/`#set_roundtime_color` rather than fixed at construction, since (unlike every vital bar's color) it changes mid-countdown. `App#run` drives a repeating one-second `GLib::Timeout` (`#tick_roundtime`) so the bar keeps ticking down between wire lines, not just when one arrives. Bars are colorized via a GTK CSS provider (`Window#load_theme_css`), one `vital-<field>` class per bar, fed from a `Theme` (`lib/grimoire/theme.rb`) built on the plain `Grimoire::Color` RGB triple (`lib/grimoire/color.rb`) — `_references/uberbar_eo.lic` was checked first and has no color/RGB data of its own (it renders through Wrayth's own named skin/image assets), so `Theme::DEFAULT` instead follows the color convention common to Simutronics-client bar mods generally (confirmed with the user 2026-09-13): background/empty `0,0,0`, health red, mana blue, stamina gold, spirit white/light-gray, mind purple, encumbrance/stance neutral gray. These are now user-configurable — see the "Configuration" section below. Bar height was also bumped to a `Window::BAR_HEIGHT = 20` CSS `min-height` default (four times the ~5px the base GTK theme renders on its own) — user-reported as too thin to read at a glance; not yet exposed as its own themeable setting, unlike the colors above.

## Configuration

- [x] YAML settings file (`configs/config.yml`; template checked in as `configs/examples/config-default.yml`; a real `configs/config.yml` is gitignored, per-user) determining default look-and-feel — `lib/grimoire/config.rb` (`Config.load`), `lib/grimoire/theme.rb` (`Theme`, a plain `Data` value object holding the merged result). Lookup order: `--config PATH` (the `grimoire` executable) > `./configs/config.yml` > `~/.config/grimoire/config.yml` > built-in `Theme::DEFAULT` if none exist — a config file only needs to mention the keys it wants to override, everything else falls back field-by-field. Colors are `"#rrggbb"` strings (`Color.from_hex`, `lib/grimoire/color.rb`), matching the format most color pickers and CSS already speak, rather than the `Color.new(red:, green:, blue:)` triple form the code uses internally. A malformed file (bad YAML, non-mapping top level, unparseable color, missing explicit `--config` path) raises `Config::Error` naming the file and the problem; the executable rescues this, warns, and falls back to `Theme::DEFAULT` rather than refusing to start.
- [x] Themeable vitals-strip/roundtime-bar colors — supersedes the former `VitalsColors` module (deleted; its fixed constants moved into `Theme::DEFAULT` unchanged), closing the "User-selectable/configurable vitals-strip colors" item this MVP had previously deferred. `theme.vitals.<field>` overrides one bar's fill color, `theme.vitals.background` the shared empty/trough color, `theme.roundtime.hard`/`theme.roundtime.cast` the roundtime bar's two colors (previously hardcoded to reuse the health/mana colors specifically — now independently configurable, defaulting to the same values for backward-compatible looks).
- [x] Themeable main input/output window colors and output font — `theme.main.background`/`theme.main.foreground` (default black background, white text, per the user's spec 2026-09-13) apply to both the scrollback `Gtk::TextView` and the command `Gtk::Entry` (`Window::OUTPUT_CSS_CLASS`/`INPUT_CSS_CLASS`, `Window#main_css`); `theme.font.family`/`theme.font.size` set the scrollback's font (Pango family name plus point size — GtkEntry has no separate font setting yet since nothing has asked for one). `font_family` is interpolated into the generated CSS raw (not force-quoted), so it can hold a full CSS font-family fallback list (e.g. `Overpass Mono, monospace`), not just a single bare name.
- [x] Bundled fonts (`assets/fonts/`, see that directory's `README.md`) — `lib/grimoire/fonts.rb` (`Grimoire::Fonts.load_bundled!`, called from the `grimoire` executable before `App.new`) registers every `.ttf`/`.otf` file under `assets/fonts/` with Pango at startup via `Pango::FontMap#add_font_file` (Pango >= 1.52), so the bundled font is usable with **no system-wide install**, confirmed end-to-end against a fontconfig environment with zero system font directories configured. This is specifically for **Overpass**/**Overpass Mono** (SIL OFL, actual font files now present in `assets/fonts/`): open source and freely redistributable, but not preinstalled on Windows the way `Monospace`'s usual fallback candidates are — bundling means grimoire's default look is consistent cross-platform rather than degrading to whatever generic monospace font Windows happens to have. `Theme::DEFAULT.font_family` is now `'Overpass Mono, monospace'` (previously the bare generic `'Monospace'`) accordingly, with the generic family still there as a fallback if `load_bundled!` ever finds nothing (older Pango, or the directory emptied out again). `assets/fonts/` is *not* gitignored — the font files are meant to be checked in.
