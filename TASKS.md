## Configuration

See [docs/configuration.md](docs/configuration.md) for the current end-user-facing settings reference (every key, type, default, description); the entries below are the implementation history.

- [x] YAML settings file (`configs/config.yml`, gitignored/per-user) determining default look-and-feel — `lib/grimoire/config.rb` (`Config.load`), `lib/grimoire/theme.rb` (`Theme`, a plain `Data` value object holding the merged result). Lookup order: `--config PATH` (the `grimoire` executable) > `./configs/config.yml` > `~/.config/grimoire/config.yml` > built-in `Theme::DEFAULT` if none exist — a config file only needs to mention the keys it wants to override, everything else falls back field-by-field. Colors are `"#rrggbb"` strings (`Color.from_hex`, `lib/grimoire/color.rb`), matching the format most color pickers and CSS already speak, rather than the `Color.new(red:, green:, blue:)` triple form the code uses internally. A malformed file (bad YAML, non-mapping top level, unparseable color, missing explicit `--config` path) raises `Config::Error` naming the file and the problem; the executable rescues this, warns, and falls back to `Theme::DEFAULT` rather than refusing to start.
- [x] Every setting is validated, not just colors — the user's own spec (2026-09-13): a `config.yml` (including a hand-edited `configs/defaults.yml` copied into a fresh one, which is otherwise never checked before being copied — the user's own observation the same day, judged acceptable to leave unvalidated at copy time since a bad value still fails loudly the next time that file is actually loaded) is free-form YAML, so nothing previously stopped a non-integer/negative `font.size`, `main.padding`, or either border `width` from silently producing broken CSS (`Window` interpolates these straight into generated stylesheet text) instead of a clear error. `Config#integer` (min `1` for `font.size`, `0` — the valid "off" value — for padding/border widths) and `Config#font_family` (must be a non-empty string) now guard these the same way `Config#color` already guarded every color field, each raising `Config::Error` naming the file, the exact dotted key (e.g. `main.border.width`), and why (`Config#color` now names its key too, previously only the file). Structural/type problems (wrong-shaped nesting under a key) still surface via the existing blanket `TypeError`/`NoMethodError` rescue in `#theme`.
- [x] Themeable window background (`theme.window.background`) — the user's own spec (2026-09-13), reported live: `padding` could already be resized but not recolored, since the gaps it creates (the outer window border and the spacing between the vitals strip/scrollback/command row, and between the individual vital bars) have no widget of their own to paint `main.background` onto, so the window's default GTK theme background (light gray in the common case) showed through regardless of any other color setting. `Window#build_window` tags the top-level `Gtk::Window` itself with a new `grimoire-window` CSS class (`Window::WINDOW_CSS_CLASS`), themed by `Window#window_css` from `Theme#window_background`, defaulting to `main_background` so the whole window reads as one consistent color out of the box.
- [x] Padding made a universal/global setting, applied consistently everywhere — the user's own spec (2026-09-13): promoted from `theme.main.padding` to its own top-level `theme.global.padding` section (`Config::KEY_PATHS`, `ConfigTemplate.render`) since it was never actually `main`-specific, and now applied two ways rather than one. As inter-widget spacing it now also covers the one gap that previously ignored it (the fixed 2px space between the vitals bars and the indicator label, `Window#build_vitals_strip`'s `strip` box) alongside its existing roles (outer window margin, the gaps between the vitals strip/scrollback/command row, between the individual vital bars). As a new second role, it is also CSS content padding *inside* every bordered widget -- the scrollback text and command entry (`Window#main_css`), and the fill within each vitals-strip/roundtime bar's trough (`Window#vital_css`/`#roundtime_css`) -- so there is breathing room between a border and its own content, not just between widgets. For the vitals/roundtime bars specifically, this could not be a plain CSS `padding:` addition on top of their existing fixed `BAR_HEIGHT`/`ROUNDTIME_BAR_WIDTH`/`ROUNDTIME_BAR_HEIGHT` (CSS padding is added on top of `min-height`/`min-width`, so it would grow the bar past those constants, breaking `ROUNDTIME_BAR_HEIGHT`'s documented exact match to `GtkEntry`'s own height): `Window#inset(total)` instead derives each trough's `min-height`/`min-width` as `total - 2x padding` (clamped at 0), so the bar's whole rendered size stays fixed at the constant regardless of `@theme.padding`'s value, with the padding visibly insetting the fill rather than growing the bar. Verified live via a rendered screenshot with an exaggerated `padding: 14` alongside colored borders: fills sit visibly inset from their borders, scrollback text has margin from its border, and the roundtime bar still matches the command entry's height exactly.

## Multi-session shell (standalone mode, phase 1)

First slice picked up from [BACKLOG.md](BACKLOG.md)'s "Standalone / multi-character mode" section (2026-09-15) — the still-Lich-backed multi-session shell, not the separately out-of-scope no-Lich EAS path below. Remaining phases (search/connect menu, headless launch, split view, per-character theming) stay in BACKLOG.md until this phase lands and they're picked up individually.

**Ordered to minimize rework** (2026-09-15), not by user-visible impact: items 1-3 are non-visual and unit-testable headlessly (matching CLAUDE.md's rule that the session/protocol layers stay testable with no live Lich or GTK), and everything needing real GTK verification lands after them. The one ordering trap deliberately avoided: building the shell before the session object exists would mean writing it against today's single-session `App` and then rewriting it — so the shell moved from first to fourth.

- [x] **1. Extract the per-character session object** — today's single-session stack (`Connection`, `CommandQueue`, `NarrativeStream`, `SessionLogger`, plus the tracker chain feeding `NarrativeStream`) comes out of `App` into one object per character, so the shell can hold N of them instead of exactly one. Landed as `Grimoire::Session` (`lib/grimoire/session.rb`), which owns that whole stack plus every callback it fires (`handle_line`, `handle_prompt`, `handle_disconnect`, `handle_send_error`) and is now the only place results are marshaled onto the GTK main thread via `GLib::Idle.add`. The key design call: **`Session` does not build its own view** — it writes through whatever it was handed as `view:` (anything answering `#append_text`/`#update_vitals`, which `Window` already did, no `Window` changes needed), so a session is independent of whether its view is a top-level window, an embeddable widget (item 3), or on screen at all (item 5). `App` keeps its exact public shape (`.new(host:, port:, ...)` plus `#run`) but is now just a `Window` + one `Session` + the GTK main loop, with the roundtime `GLib::Timeout` calling `Session#tick` (still deliberately unmarshaled — a `GLib::Timeout` callback is already on the GTK main thread). Private `handle_command`/`tick_roundtime` became public `Session#send_command`/`#tick`, since the shell needs to drive them from outside. Character name is now carried on the session (`Session#character`, nil for a raw `--host`/`--port` with no name to go with it) and wired through from the executable's `--character` flag, which previously resolved a name to host/port and then discarded it — item 2 is its first consumer. `App`'s window builds its `on_command` callback as a lambda closing over `@session` rather than referencing it directly, since the window must exist before the session that draws into it. New `spec/grimoire/session_spec.rb` covers the session against a plain fake view with no GTK widgets involved at all (including a verifying `instance_double(Grimoire::Window)` example that fails if `Session` ever calls something `Window` does not define — a guard specifically for item 3's `Window` rework); `app_spec.rb` slimmed to App's own job (window/session wiring, option pass-through) while keeping the real-`Window` end-to-end examples. Verified beyond the suite by driving the real `App#run` against a fake Lich socket: handshake sent, narrative text rendered into the real scrollback, auto-`look` fired and echoed on first prompt, health bar at 0.87 on the real widget.
- [x] **2. `SessionLogger` keyed off character name** instead of port for its log filename, so concurrent sessions in one process get deliberately-named logs rather than differently-named-by-accident ones. `SessionLogger.new` gained an optional `character:` alongside its existing `port:`, and picks the label itself (`#session_label`) rather than having the caller decide: the character name when one is usable, the port otherwise — a raw `--host`/`--port` launch has no name, so the old `session-<port>-<stamp>-{raw,parsed}.log` naming is still exactly what it produces, unchanged. `Session` passes its own `character` (from item 1) straight through. Two things the name needed on the way to a file path: it is **sanitized** (`SessionLogger::UNSAFE_LABEL_CHARACTERS`, anything outside `[A-Za-z0-9_-]` dropped) because `--character NAME` is arbitrary user input heading into `File.join` — a path-separator or traversal name must not be able to write outside the log directory — and it is **case-normalized** the same `downcase.capitalize` way `SessionLocator` already normalizes a name into lich-5's own session-file name, so `--character sparrow` and `--character Sparrow` produce one set of logs rather than two differing only in case. A name that sanitizes away to nothing falls back to the port. Covered in `session_logger_spec.rb` (character naming, case normalization, two characters at one timestamp, traversal/absolute-path names, empty-name fallback) plus a `session_spec.rb` case pinning that the session hands its character down. Verified end to end by running the real `App#run` with `--autolog` against a fake Lich socket as `sPaRrOw`: produced `session-Sparrow-<stamp>-raw.log` and `-parsed.log`, raw carrying the `progressBar` tag and parsed carrying only the narrative text.
- [ ] **3. `Window`'s content becomes an embeddable widget** (not its own top-level `Gtk::Window`), ready to be switched via a `Gtk::Notebook` top tab bar — GNOME-Terminal-style, chosen over a `Gtk::Stack` + `Gtk::StackSidebar` left-hand list (user's own call, 2026-09-15). Independent of items 1-2 (different file), but a prerequisite for item 4. Still displayed inside a single top-level window at this point, so no behavior change yet and it can be verified in isolation.
- [ ] **4. Blank-start shell window with a menu bar and the `Gtk::Notebook` tab bar**, no character connection required at launch — `App#run` today assumes host/port are already known and connects immediately; a no-args launch mode needs to skip straight to `Gtk.main` with nothing connected yet. `--character NAME`/`--port PORT` keep working but change meaning: they open the shell with that session pre-attached as the first tab, rather than staying a separate no-shell code path. Written once, correctly, now that it can hold N session objects (item 1) each with an embeddable view (item 3). One top-level shell window total.
